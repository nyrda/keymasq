# Keymasq agent reference: profiles and actions

Use this file for profile TOML, mapping actions, rapidfire, tap, and window
rules.

Profiles live at:

```text
~/.config/keymasq/profiles/<profile_name>.toml
```

Profiles are global remap layers, not per-device configs. A profile can
contain layers for multiple hardware IDs. Active profiles are merged; later
active mappings win. Conditional profiles override permanent profiles when
their window rules match.

## Basic profile

```toml
[profile]
name = "Gaming"
enabled = true
is_permanent = true
priority = 0
notify_on_activation = true
created_at = "2026-03-09T12:34:56"

[devices."1234:5678"]
always_grab_all = false

[devices."1234:5678".mapping.btn_back]
action = "keyboard"
target = "key_1"
```

## Conditional profile

```toml
[profile]
name = "Firefox"
enabled = true
is_permanent = false
priority = 50
notify_on_activation = true
created_at = "2026-03-09T12:34:56"

[[profile.window_rules]]
field = "class"
pattern = "firefox"
```

Portable window rule fields are `class` and `title`. Patterns are regular
expressions. All rules in one profile must match.

Compositor-specific fields:

- `tag`: Hyprland window tags.
- `layer`: namespace of the layer-shell surface with keyboard focus, such as a
  launcher (fuzzel uses `launcher`). Hyprland only. While a layer has focus,
  class, title, and tags are empty.

## Device layers and mappings

```toml
[devices."<hardware_id>"]
always_grab_all = false

[devices."<hardware_id>".mapping.<source_button_id>]
action = "<action>"
```

Unlisted inputs pass through unless another active profile maps them.
`always_grab_all = true` captures all input from that device while the layer is
active.

## Action fields

```toml
# pass original input through
action = "passthrough"

# block input
action = "suppress"

# repeat the last remembered action
action = "repeat"
# optional; defaults to all categories:
repeat_categories = ["keyboard", "mouse", "gamepad", "macro", "special"]

# output keyboard key
action = "keyboard"
target = "key_space"

# output mouse button or wheel direction
action = "mouse"
target = "btn_left"

# output virtual Xbox-style gamepad button
action = "gamepad"
target = "btn_x"
# optional strict output route:
# output_id = "virtual-gamepad-2" # or configured hardware gamepad ID

# control tracked MPRIS media players
action = "mpris"
command = "play_pause"

# run shell command in the user's session
action = "exec"
cmd = "notify-send keymasq"

# move cursor
action = "mouse_move_rel" # or "mouse_move_abs", "mouse_move_natural_abs"
x = 100
y = 0

# natural absolute cursor movement uses relative uinput events plus realtime
# cursor feedback; supported on GNOME, Hyprland, KDE Plasma, X11, and
# Wayland compositors with zwlr_layer_shell_v1 plus zxdg_output_manager_v1
action = "mouse_move_natural_abs"
x = 640
y = 480
speed = 12000.0
curve = "natural" # linear or natural
jitter = 0.3
tolerance = 2
max_duration_ms = 3000
# a plain mapping or combo runs the move in the background: other keys keep
# working, key release does not stop it, emergency reset does; later natural
# moves wait for it. In superkeys and analog thresholds the following actions
# wait until it ends, and other input can be held back until then.

# play saved macro by name; only these playback fields are per mapping.
# loop_mode, loop_count, loop_stop_behavior, pause_timeout_s,
# block_mouse_movement, and block_keyboard belong to the saved macro and are
# ignored on mappings (see agents/macros.txt)
action = "macro"
target = "macro_name"
replay_mouse_movement = true
replay_mouse_clicks = true
speed = 1.0

# control profiles
action = "profile_toggle" # or profile_enable, profile_disable
profile_name = "Gaming"
target = "Gaming"

# compositor dispatch
action = "compositor_dispatch"
compositor = "hyprland" # hyprland, niri, sway, kde, gnome
dispatcher = "hl.dsp.window.fullscreen({ mode = \"fullscreen\", action = \"toggle\" })"
args = ""
# sway takes its command language, split across dispatcher and args:
# compositor = "sway", dispatcher = "workspace number", args = "2"

# superkey
action = "superkey"
superkey_name = "Nav Layer"

# analog control
action = "analog_control"
analog_control_name = "FPS Mouse"

# macro controls
action = "start_macro_recording"
recording_slot = 1
action = "stop_macro_recording"
recording_slot = 1
action = "play_macro_slot"
recording_slot = 1
action = "cancel_macro_playback"
```

## Rapidfire and tap

Rapidfire emits repeated output pulses while the physical source is held.
Supported by `keyboard`, `mouse`, `gamepad`, `mouse_move_rel`, and
`mouse_move_abs`. Natural mouse movement is not rapidfire-capable. Repeat
actions also store rapidfire fields, but Repeat only applies them when the
remembered action is a keyboard key, mouse button, mouse wheel action, or
gamepad button.

```toml
rapidfire_enabled = true
rapidfire_hold_ms = 10 # press duration per pulse, min 0
rapidfire_wait_ms = 10 # gap after release before next pulse, min 1
```

Tap sends one short pulse even if the physical source is held:

```toml
tap_enabled = true
tap_hold_ms = 10
```

Rapidfire and tap are mutually exclusive.

## Rollover groups

A rollover group lists source buttons, on one or more devices. At most one held
member is active, and only its mapping reaches the outputs. Use it for two keys
on one stick axis (releasing one no longer centers the stick while the other is
held) or for Snap Tap style keyboard output. Groups are top-level profile
tables, not part of a device layer.

```toml
[[rollover_groups]]
name = "A / Side"
members = [                  # in priority order
  { hardware_id = "1234:5678", button = "key_a" },
  { hardware_id = "046d:c52b", button = "btn_side" },
]
winner = "newest"            # newest, oldest, neutral, or priority
restore = true               # a still-held member takes over again
```

- `newest`: the most recently pressed member is active.
- `oldest`: the first pressed member is active. Later members wait.
- `neutral`: two or more held members release the output.
- `priority`: the held member listed first is active.
- `restore = false`: a member that lost while held stays inactive until it is
  pressed again.

Members may use any action, or be unmapped (they pass through). Gaining the
active role presses the member's action and losing it releases the action, like
a real key press, so tap, rapidfire, macros, and superkeys restart on every
handover. A running tap ends at once when a member sending the same plain
output, or a non-plain one, takes over. Press-only actions (exec, compositor dispatch, profile enable,
disable and toggle, mpris, macro slot and recording controls, emergency reset)
run once per physical press, not again on each takeover. Two members that send the same plain key, button, or axis target
without tap or rapidfire hand over by overwriting it, without a release. A
member belongs to one group. A group in a higher-priority profile replaces
lower groups that share a member. Groups need at least two members, each with
`hardware_id` and `button`. A member listed twice, a member in two groups of
one profile, an unknown `winner`, or a non-boolean `restore` fails the profile
load (logged; a live reload keeps the old config and notifies).
Members on a device that no profile maps still get their interface grabbed.
When a device disconnects, its held members count as released.

## Repeat action

`action = "repeat"` replays the newest remembered action whose category is
enabled by `repeat_categories`. Valid categories are `keyboard`, `mouse`,
`gamepad`, `macro`, and `special`. Legacy `mouse_button` and `mouse_wheel`
values are normalized to `mouse`.

`mouse` covers mouse buttons and wheel directions. Configured
`mouse_move_rel`, `mouse_move_abs`, and `mouse_move_natural_abs` actions are
`special`; raw passthrough mouse movement is not recorded. Repeat does not
remember Repeat, passthrough mapping actions, suppress actions, profile actions,
emergency reset, or unresolved top-level superkey bindings. For superkeys, the
top-level binding
itself is not stored
verbatim; Repeat stores the resolved slot/overload path (not the original
top-level superkey binding), so repeated Repeat invocations replay the resolved
action. Repeating an action refreshes the Repeat history with the resolved
action, so repeated presses of Repeat continue replaying it.
Superkey paths that contain profile actions are not stored.

## Common snippets

Make source button `btn_x` output virtual gamepad X rapidly:

```toml
[devices."1234:5678".mapping.btn_x]
action = "gamepad"
target = "btn_x"
rapidfire_enabled = true
rapidfire_hold_ms = 10
rapidfire_wait_ms = 10
```

Make mouse side button click left rapidly:

```toml
[devices."046d:c548".mapping.btn_back]
action = "mouse"
target = "btn_left"
rapidfire_enabled = true
rapidfire_hold_ms = 10
rapidfire_wait_ms = 10
```

Map a gamepad stick source to an Analog Control config:

```toml
[devices."045e:028e".mapping.right_stick]
action = "analog_control"
analog_control_name = "FPS Mouse"
```

Analog Control configs live under `~/.config/keymasq/analog_controls/`:

```toml
name = "FPS Mouse"
input_type = "stick"

[mouse_motion]
enabled = true
speed = 900.0
speed_x = 900.0
speed_y = 900.0
deadzone = 0.15
sensitivity = 1.0
response_curve = 1.0
invert_x = false
invert_y = false
tick_ms = 8

[gamepad_output]
enabled = false
output_id = "virtual-gamepad-2"
deadzone = 0.0
target = "same"
sensitivity = 1.0
response_curve = 1.0
output_invert_x = false
output_invert_y = false

[[thresholds]]
axis = "x"
trigger_min = 0.65
trigger_max = 1.0
release_min = 0.55
release_max = 1.0
actions = [
  { action = "keyboard", target = "key_e" },
]
```

Axis Analog Controls use `input_type = "axis"`, one threshold axis
(`axis = "x"`), and signed threshold ranges from `-1.0` to `1.0`.

Map a hardware motion sensor to a saved Motion Control:

```toml
[devices."054c:0ce6".mapping.motion_1]
action = "motion_control"
motion_control_name = "Gyro Aim"
```

Attach multiple Motion Controls to the same sensor by replacing the singular name with an
ordered list:

```toml
[devices."054c:0ce6".mapping.motion_1]
action = "motion_control"
motion_control_names = ["Gyro Aim", "Tilt Directions"]
```

Motion Controls live under `~/.config/keymasq/motion_controls/`. Their `mode` is `mouse`,
`gamepad`, `tilt_mouse`, `tilt_gamepad`, or `analog`. The top-level
`[axis_routing]` table configures gyro controls. It assigns each of `yaw`, `pitch`, and
`roll` to `none`, `horizontal`, or `vertical`.

Accelerometer controls use the `[tilt]` table. `pitch` and `roll` select the output channel;
`reference` is `activation` or `gravity`; `deadzone_deg` and `full_scale_deg` set the angular
range. Tilt Mouse uses `speed_x` and `speed_y`. Tilt Stick uses the single output route from `[gamepad]`.
Raw-unit calibration and driver-specific axis normalization remain in the hardware file.

`mode = "analog"` uses the `[analog]` table. `source` is `gyro` or `tilt`; `x_axis` and
`y_axis` select the canonical signal; `analog_control_name` names one saved Analog Control.
Gyro sources accept `yaw`, `pitch`, `roll`, or `none`. Tilt sources accept `pitch`, `roll`,
or `none`. `full_scale_dps` and `full_scale_deg` define the physical value that becomes a
normalized magnitude of `1.0`. Axis Analog Controls consume X only, while stick controls
consume X and Y. Motion to Analog always uses timestamp-based One Euro filtering before the
Analog Control processes the normalized axes. `adaptive_min_cutoff_hz` defaults to `1.0` and
accepts `0.1` to `10.0`; lower values suppress more resting jitter but add slow-motion delay.
The GUI exposes this as Steadiness from 0 to 100, with cutoff = 10^(1 - steadiness/50).
The midpoint of 50 corresponds to the default 1 Hz; 0 still applies light smoothing.
`adaptive_beta` defaults to `10.0` and accepts `0.0` to `100.0`; higher values reduce delay
while moving but pass more noise. The derivative cutoff is fixed at 1 Hz. Beta applies to
normalized input, so its units do not change between gyro and tilt sources. Filter state is
separate for each control and axis and resets with the mapping, dropped input, a gap over
0.5 seconds, or backwards input timestamps.

Map a mouse's pointer movement with the `pointer` source ID. It exists for hardware with a
mouse event device, or one reporting `rel_x` and `rel_y`, and needs no hardware entry.
Mouse mode scales counts and writes them to the mouse's passthrough device:

```toml
[devices."046d:c08b".mapping.pointer]
action = "pointer_movement"
mode = "mouse"
factor_x = 1.0
factor_y = 2.0
```

Axes mode drives controller axes instead of the pointer. `x_axis` and `y_axis` take any ABS
axis name or `none` (defaults `abs_rx` and `abs_ry`). `x_direction` and `y_direction` are
`both`, `max`, or `min`; one-way output uses positive movement after inversion.
`behavior = "velocity"` uses `full_speed` in counts/s averaged over `window_ms`.
`behavior = "position"` uses `radius` in counts, `overshoot` (`drag` or `keep`), and
`recenter_ms` (0 = off). `output_id` defaults to Virtual Gamepad 1. In both modes,
`swap_axes` applies first, then `invert_x`/`invert_y` and `factor_x`/`factor_y` on the
swapped channels. `deadzone`, `minimum_output`, and `response_curve` shape each axis:

```toml
[devices."046d:c08b".mapping.pointer]
action = "pointer_movement"
mode = "axes"
behavior = "position"
radius = 1500.0
overshoot = "drag"
x_axis = "abs_x"
y_axis = "abs_rz"
y_direction = "max"
invert_y = true
```

`action = "suppress"` on `pointer` blocks pointer movement, and `action = "passthrough"`
restores normal movement over a lower-priority profile's pointer mapping.
Ranges: `factor_x`/`factor_y` 0-50, `full_speed` and `radius` 1-1000000, `window_ms`
4-250, `recenter_ms` 0-60000, `deadzone` and `minimum_output` 0-0.95, `response_curve`
0.25-4. An unknown choice or axis name, an out-of-range number, or a wrong type fails the
profile load (logged; a live reload keeps the old config and notifies). Negative factors are
invalid; use `invert_x`/`invert_y`.

Bind a saved macro:

```toml
[devices."1234:5678".mapping.btn_extra]
action = "macro"
target = "double_click_10ms"
speed = 1.0
```

Loop, release, pause, and input-blocking settings come from the saved macro.

Bind a saved superkey:

```toml
[devices."046d:c548".mapping.btn_forward]
action = "superkey"
superkey_name = "copy_or_paste"
```

Combo definitions are stored inside profile TOML. For combo examples and
superkey file format, fetch:

```text
https://keymasq.tools/docs/latest/agents/superkeys-combos.txt
```
